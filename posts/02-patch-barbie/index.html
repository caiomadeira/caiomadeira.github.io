Patching Barbie Detective 2

11 Jan 2026

The patch and files can be found in my github repo.

Someday my girlfriend says to me that was a childhood barbie game that’s she plays a lot of and when show me i was surprised. I’ve never ssen a game with such awful controls, but, yeah…It’s 1999. So, not too long ago, we’ve looking for play this gem and we depare with the ISO on My Abandon Ware and we download. Right from the start we encountered a problem (a couple of, btw), when barbies enters into the “maze garden”, the game crashes.

After this entrance, the faithful destiny waits. Of course that one old game brings problem when people runs on modern operation systems. The comment section of AbandonWare show us a proof of that. Actually, to make this game run, you need of a Virtual Machine and runs it on Windows 95 - which is quite bad. So, i think we can make this scientific contribution to community (at least try abd have fun).

As part of ‘Detective Barbie Series’, ‘Detective Barbie 2: The Vacation Mystery’ was released for Microsoft Windows in 1999. I’m not sure but most people probably played this on Windows 95/98(?) and that’s was a period of transition (16 to 32 bits). Tha’ts why we face the first big problem: the installation of CD-ROM.

Installation

Today we don’t use Daemon Tools to mount ISO files anymore, the Windows 11 it’s self has the functionallity (which is great), but the actually windows, despiste maintaining compatibility with legacy softwares pieces, it’s a magic box; what wil work or go wrong. The first issue is, the SETUP.EXE is for 16-bit systems, which force me to look to approachs with otvdm: which allows us to execute old windows 16 bits applications on 64 bits windows versions. Unfortunelly, this approach stucks on “no high privileges loop” and nothing in the world can lead with this. The second approach was the UniExtract3 (for extract files). My logic is: if i can’t use the installator, i just mount the game files by my self. That would be good if the installer were responsible for decompressing file (which i think is true since there were .cab files), but that’s is another shot in the dark because, if there’s only one hardcoded path referring to the assets, i’ll, possibly, introduce a new crash. And the last was use a generic installer of Install Shield 3 (which is the same as used by the barbie wizard), but, honestly, i don’t even remember why i chose that approach. I just dropped the executable into the same folder and hoped.

In the end, i just use the auto installer marking with windows compatibillity mode and set to run as administrator and worked. :D

Compatibillity problems (of course)

So, with the game installed, let’s begin the real analysis. I started open the x32dgb and open the d2.exe (the executable of the game), but here another problem. If i run the game by x32dg and make all the path to the crash site, the game freeze and stay on black screen and i can’t proceed with debug because he refuses to minimze. By that, i opt to Attach the game process after run the program and this is simple right? No, because a lot of dummy instances of the game was running. Close after crash its a nightmare.

One thing that i tried was the DxWnd with the objective to “translate” the old windows graphical calls to moderno windows 10/11. I’ve tested with GDI and DirectX configurations such a 16 BPP for color settings.

Binary analysis with debugger

Before start playing the game until the maze garden entrance, i need to check some configurations on Configs tab. I leave with default Unknown exceptions and marked First chance for x32debug catch on the first any exception that’s may occur on the way. Before it, my goal is to setup a range like the image bellow.

What this means? The range [00000000, FFFFFFFF] is choosed here because the d2.exe architecture is 32-bits (x86) - don’t confuse this with the installator that was 16-bits - so the memory are adressed in range of [0, 2^32 - 1]. The 00000000 is the first memory address possible and the FFFFFFFF is the last (4 GB). Configurate this means that x32debug can catch all type of exceptions, regardless of its origin. If the error comes from a game code, windows DLL or video driver. If any byte inside all acessible memory throws some error, the x32debug will catch. The “first chance” simply, when a exception occurs, make the x32debug takes the first action (and pause the program) before the program, that is being analyzed, knows. The first chance option was crucial to analyse the Stack and registers state on the exactly moment of the exception.

When i achieved the moment of crash, the debugger stops (EIP stops on 7644161C address) on the instruction ret 4 inside the win32u.dll. I was inside a system lib, seeing stubs from syscalls. The ret 4 instruction is an specific for x86 architecture and it’s been used in the end of a subroutine for return the control for the “call code” and then adjust the stack pointer (ESP) on 4 bytes for remove args than has been passed. The ret 4 takes on parameter, but variations exists like ret 8 which takes two (32-bits each).

For better investigation, i look to value that ESP register points and the memory stack on debugger. My best guess is still some kind of compatibilty issue between the old graphical interface and modern Windows. The stack area give some clues about.

We can see return to user32.DrawStateW+1196. I assume that the game asks for windows draws something on the screen using the DrawState function. Maybe in some point of this process of drawing, there was an attempt to adjust some GUI element focus to receive the user input (NtUserSetFocus) and thats the error appears. I don’t saw much relationship with this NtUserSetFocus and the fact that i was inside of a syscalls made debugging even more of a shot in the dark. So a decide to restart the game and be more faster immediatelly after the crash and make all the process again.

New clues

With this run, the history change, on the CPU tab, in the line 00474C3C, now, we can see push d2.493808 and on the side, in the debugger comments, the ERROR message. Above that, the instruction call dword ptr ds:[<MessageBoxA>] that make a call to MessageBoxA windows standard function (just shows a message box/an alert) and, in the end, he calls the PostQuitMessage.

My new theory is: the game detects an intern problem and he decides to inform this to the user (through a MessageBox) possibly with the “ERROR” message. What i’m not sure about is whether NtUserSetFocus has anything to do with a possible error in the attempt to draw that error box. The win32u crash seens more like a collateral effect of all this.

After this, a take a look to the Call Stack tab again. My actual step is d2.00474C50 and the suspect is ```d2.00407066. The function on 00407066 can be causing this probloem calling the error screen or something like that.

Going to this address (00407066), we are taken to the game code, right after the error function call, where i looked for instructions like CMP or TEST (comparison) and JNZ, JE and JZ (conditional jumps).

The one to blame

Looking at 00407057 we can see the instruction CMP EAX, EBX. This means that the game is comparing two values. EAX usually contains the result of previously function (i cut them from print, sorry) and EBX is the expected value (maybe some success code or 0).

The second important line is the address 0040705E referring to the instruction JNE d2.407069. JNE stands for “jump if not equal”. If the EAX (result) is different of EBX, the game says: “Ok, all good.” and jumps to the 407069 address, continuing the execution normaly. The crash says that this comparison results in a equal value, so the JNE don’t jump.

Since the jump did not occur, the processor pass to the bottom line with the address 00407061. This line make a call to some function (CALL d2.474C30) and this function show the ERROR message and closes the game.

Patching the binary

Initially, i consider make a wrapper instead of a patch on assembly, because the wrapper seens more secury, but i preferred to take the risk of a patch.

The goal is simple: make the game code always jump this verification, no matter what it is. So i change the jne d2.407069(75 09) on address 0040705E to jmp d2.407069(EB 09). I forced the game to continue even though something went wrong and worked (this could have gone very wrong).

The rest is rotine. I create a new executable for the game and post on my Github repository.
